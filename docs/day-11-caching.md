### Part 0 Questions & Answers

1. **Which endpoint has the best ratio?**
   * **Store details** has the best reads-per-change ratio. It is read frequently when users visit a store page, but the store metadata (name, description, location) changes extremely rarely.

2. **Which would be a bad thing to cache, and why?**
   * **Product text search** is bad to cache because the search queries are generated by free-form user input. The input space is virtually infinite, meaning query keys rarely repeat. Caching them would consume valuable Redis memory (a memory leak with a TTL) without providing any benefits.
   * **My orders** is also sub-optimal because it is partitioned per customer. A cache hit only occurs if the exact same customer requests their order history multiple times within the TTL window, which is very rare in regular use.

3. **The store sales tally changes on every single order. But look at what it already is — a table that your analytics consumer keeps up to date, read back with one tiny query. Would putting a cache in front of it buy you anything? Say why or why not.**
   * **No.** Since the sales tally is pre-aggregated and kept up to date by the analytics consumer, querying it is a fast primary key lookup. Adding a cache in front of it adds Redis network latency, serialization overhead, and invalidation complexity for no noticeable latency or throughput improvement.

## Part 2 — The key: every input, and only inputs that repeat

### Cache Key Structure (Browse List)
The cache key incorporates all input query parameters that affect the result output to avoid serving wrong pages or wrong sorts to users:
```
store:{storeId}:products:cat:{categoryId}:sort:{sortBy}:{sortOrder}:page:{page}:size:{pageSize}
```
* **Inputs included**: `storeId` (or `0` if null), `categoryId` (or `all` if null), `sortBy` (or `name` if null), `sortOrder` (or `asc` if null), `page`, and `pageSize`.

### Page Size Clamping
We enforce clamping on the incoming `pageSize` input directly in the API layer, allowing only **10**, **20**, or **50** items per page. If a client sends any other value, it is automatically clamped to **20**.
* **Reasoning**: If the client were allowed to request any arbitrary size (e.g. `21`, `22`, `37`), an attacker or custom client could generate an infinite number of unique cache keys for the exact same dataset, rapidly exhausting Redis memory. Clamping reduces the key space size significantly.

### Missing Input Bug Analysis
If page number (`page`) is left out of the cache key:
* A request for `page=1` misses, fetches page 1 data, and caches it under a key like `store:1301:products:cat:all...`.
* A subsequent request for `page=2` builds the exact same key. It hits the cache and returns **page 1 data again**. The customer is shown duplicate data and cannot browse past the first page until the TTL expires.

### Text Search and Price Filter Bypass
We deliberately bypass the cache for any search request containing a text term (`text`) or price bounds (`minPrice`, `maxPrice`).
* **Reasoning (Menu vs. Typed Inputs)**: Menu inputs like category, sort order, and page size are chosen from a small, fixed list of options, meaning they repeat frequently across all users. In contrast, text search terms are typed by humans and price boundaries are highly variable. They rarely repeat. Storing them in cache leads to write-once-read-once waste (memory bloat) instead of actual cache reuse.
